# Briefing Pereda Dev — Testar localmente e subir para o Git

## 1. Entrar na pasta do projeto

```powershell
cd "C:\Users\marce\Projetos\Projetos finalizados\projeto\pereda-dev\BRIFING\briefing\briefing"
```

---

## 2. Testar localmente

Como o projeto possui uma API em:

```text
/api/briefing.js
```

usar o ambiente local da Vercel:

```powershell
npx vercel dev
```

Depois abrir no navegador:

```text
http://localhost:3000
```

Testar:

* as 6 etapas;
* voltar e avançar;
* validações;
* selects;
* materiais;
* modo claro/escuro;
* mobile;
* envio;
* tela de sucesso;
* recebimento do e-mail.

Para parar o servidor:

```text
Ctrl + C
```

---

# 3. Conferir o Git

Depois de fazer alterações:

```powershell
git status
```

Isso mostra quais arquivos foram modificados.

---

# 4. Conferir se o `.env` está protegido

O `.env` **não deve ir para o GitHub**.

Verificar:

```powershell
git check-ignore -v .env
```

Se aparecer uma linha indicando `.gitignore`, está correto.

---

# 5. Adicionar as alterações

Se quiser adicionar tudo que foi alterado:

```powershell
git add .
```

---

# 6. Conferir antes do commit

```powershell
git status
```

Confira se:

```text
.env
```

não aparece entre os arquivos que serão enviados.

---

# 7. Criar o commit

Exemplo:

```powershell
git commit -m "fix: ajusta briefing e validações"
```

Use uma mensagem que descreva o que realmente foi alterado.

---

# 8. Enviar para o GitHub

```powershell
git push
```

O repositório do Briefing é:

```text
https://github.com/marceloperedadev/peredadev-briefing.git
```

Se for a primeira vez que a branch estiver sendo enviada:

```powershell
git push -u origin master
```

Depois disso, normalmente apenas:

```powershell
git push
```

---

# 9. Fluxo que devo seguir sempre

Sempre que alterar o Briefing:

```text
ALTERAR CÓDIGO
      ↓
TESTAR LOCALMENTE
      ↓
npx vercel dev
      ↓
http://localhost:3000
      ↓
TESTAR ENVIO/API
      ↓
git status
      ↓
git add .
      ↓
git commit -m "..."
      ↓
git push
```

---

## Atenção

Nunca colocar a chave da Resend diretamente no código ou no GitHub.

O `.env` deve continuar no `.gitignore`.

Exemplo:

```env
RESEND_API_KEY=re_SUA_CHAVE
RESEND_FROM_EMAIL=onboarding@resend.dev
```

A chave real deve ficar somente nas variáveis de ambiente locais/Vercel.
